# 内测验证接口 — 实现说明

> 本文档说明 `northstar_backend` 中「北极战区内测资格校验」的实现方式、部署配置与自测方法。
> 完整的**字段级契约**见客户端仓库的
> `NorthStarClientverification/docs/NorthStar-内测验证接口文档.md`（v3.5）。
>
> **v3.0 核心变化**：北极战区是**离线模式**服务器，玩家 UUID 由各启动器自行生成、
> 每次启动都可能不同，**不能作为身份依据**。因此身份判定改为
> **QQ + 游戏ID（`mcId`）**，`uuid` 参数已从接口中移除。
>
> **v3.1 补充**：服务端**不启用 MC 白名单**，判定完全在后端做。为了让「审批通过」真的能放行，
> 注册平台新增 QQ 字段（`POST /api/auth/register` 的 `qq`），内测审批通过时后端会
> **自动把该玩家的「QQ + 离线服游戏 ID」同步成白名单条目**，运营不必再手工维护。详见 §5.3。
>
> **v3.5 补充**：**内测申请必须登录平台账号**。申请记录直接挂在 `users.id` 上，QQ 与游戏 ID
> 一律从账号读取、请求体里带什么都不作数——所以不会出现「拿别人的 QQ 替别人占名额」。
> 前端配套把申请区从「查询失败才出现」提升为独立区块，未登录只给登录 / 注册入口。详见 §5.6。

## 2. ⚠️ 三条不能碰的红线

客户端 Mod 的判定逻辑是「先看 HTTP 状态码，再看 `success` / `code`」，改动接口时必须守住：

1. **「明确未通过」必须返回 `HTTP 200` + `success:false` + `code:1001`。**
   这是唯一会让玩家客户端**生成崩溃报告并退出游戏**的响应 —— 这是设计如此，不要"优化"成 4xx。

2. **服务异常必须返回非 2xx（400/429/5xx）。**
   一旦服务异常也返回 `200 + success:false`，会把**全体玩家**踢出游戏。客户端对非 2xx **完全不解析响应体**，只看状态码。

3. **`success` 必须是 JSON 布尔值。**
   数字 `1` 会被判为「服务不可用」（玩家反复重试）；字符串 `"1"` 会被判为「未通过」（玩家崩溃）。

另外：**接口 A 的响应体不能套 `ApiResponse`**（不能写成 `{"code":200,...,"data":{...}}` 再往里塞）。
客户端支持 `code:200` 只是兼容性兜底；`success` 是首选字段，务必保留。

## 3. 判定与状态码一览

判定顺序（`BetaWhitelistService.verify`）：

| # | 场景 | HTTP | 响应体要点 | 玩家体感 |
| --- | --- | --- | --- | --- |
| 1 | `qq` 格式非法 | 400 | `success:false, code:4000` | 停在验证界面可重试 |
| 2 | `name`（游戏ID）为空 | 400 | `success:false, code:4000` | 停在验证界面可重试 |
| 3 | 单 IP 超限流 | 429 | `success:false, code:4290` | 停在验证界面可重试 |
| 4 | QQ 不在白名单 | 200 | `success:false, code:1001` | **崩溃退出** |
| 5 | 有记录但全部禁用 / 已过期 | 200 | `success:false, code:1001` | **崩溃退出** |
| 6 | 可用记录且 `mcId` 与 `name` 一致（忽略大小写） | 200 | `success:true, code:0` | 正常进入游戏 |
| 7 | 可用记录且 `mcId` 为空 | 200 | `success:true, code:0` | 正常进入游戏 |
| 8 | 可用记录但绑定了别的游戏ID | 200 | `success:false, code:1001` | **崩溃退出** |
| 9 | 内部异常（DB 等） | 500 | `success:false, code:5000` | 停在验证界面可重试 |

> 第 7 条（未绑定游戏ID 放行）可用 `northstar.verify.require-mc-id=true` **关闭**。
> 第 2 条**故意返回 400 而不是 1001**：离线模式下 `name` 是唯一身份依据之一，缺失说明客户端
> 调用有误，属于「可重试」而不是「判定为不合格」，否则会误崩合法玩家。

### 3.1 拒绝原因文案（写入日志；也会出现在崩溃报告的「响应内容」里）

| 场景 | `reason`（日志，128 字符内） | `msg`（响应体） |
| --- | --- | --- |
| QQ 不在白名单 | `QQ 不在白名单` | `该 QQ 未获得内测资格` |
| 资格被禁用 | `资格已被禁用` | `该 QQ 的资格已被禁用` |
| 资格已过期 | `资格已过期` | `该 QQ 的资格已过期` |
| 游戏ID 不匹配 | `游戏ID 与绑定不一致（已绑定 Steve）` | `游戏ID「Alex」与白名单绑定的不一致（已绑定：Steve）` |
| 要求绑定但未绑定 | `该 QQ 未绑定游戏ID` | `该 QQ 未登记游戏ID，请联系管理员补充绑定` |

## 4. 配置

`application.properties` 新增三项，都有安全默认值：

```properties
# 与客户端 qqPattern 保持一致，改动需两侧同步
northstar.verify.qq-pattern=${VERIFY_QQ_PATTERN:^[1-9]\\d{4,10}$}
# 每来源 IP 每分钟允许次数，<=0 关闭限流
northstar.verify.rate-limit-per-minute=${VERIFY_RATE_LIMIT_PER_MINUTE:60}
# 是否强制要求白名单条目已绑定游戏ID（mcId）
northstar.verify.require-mc-id=${VERIFY_REQUIRE_MC_ID:false}
```

> ⚠️ **`require-mc-id=true` 之前必须确认白名单里每条都填了 `mcId`**，否则这些 QQ 的玩家会**全部崩溃**。

### 4.1 反向代理必须写 `X-Forwarded-For`

服务端按 `X-Forwarded-For`（取第一个）→ `X-Real-IP` → `remoteAddr` 取客户端 IP。
生产环境前面是 Nginx / OpenResty 时，**若反代没有写入 `X-Forwarded-For`，所有玩家的 `remoteAddr` 都是 `127.0.0.1`，限流会把全体玩家当成同一个人**。

Nginx 参考：

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

### 4.2 建议在反代日志中对 `qq` 脱敏

接口是 GET，QQ 会进访问日志。可在 Nginx 用 `map` + `log_format` 把 `qq=123456789` 改写成 `qq=123****89`。
后台接口 `/verify-logs` 默认已脱敏（`showQq=true` 可看完整值）。

## 5. 数据库

`ddl-auto=update`，启动时自动建表，无需手工执行 DDL。

- `northstar_beta_whitelist`：唯一键是 **`(qq, mc_id)` 组合**（`uk_beta_whitelist_qq_mcid`）。
  同一个 QQ 可以绑多个游戏ID（例如小号）；`mc_id` 为 NULL 表示「只绑 QQ，不限定游戏ID」。
- `northstar_verify_log`：每次校验写一条，增长较快。后台日志查询固定只取**最近 1000 条**再过滤分页；
  建议按 90 天做归档/清理（可用定时任务删除 `created_at < now - 90d`）。

### 5.1 `mc_id` 的语义（**v3.0 起参与校验**）

| `mc_id` | 含义 | 校验行为 |
| --- | --- | --- |
| 有值（如 `Steve`） | 该 QQ 绑定到这个游戏ID | 上报的游戏ID 必须一致（忽略大小写），否则**判未通过** |
| `NULL` / 空 | 只绑 QQ，不限定游戏ID | 任意游戏ID 都放行；`require-mc-id=true` 时改判**未通过** |

> 后台列表返回的 `gameIdBound` 字段就是「是否已绑定」，建议前端对 `false` 的行加醒目提示。

### 5.2 🔧 从 v2.0 升级（**必须手工处理索引**）

`ddl-auto=update` **只会新增、不会删除**旧索引和旧列。若在 v3.0 之前已经启动过服务建过表：

```sql
-- 查看现有索引（v2.0 时代 qq 上有一个单列唯一约束）
SHOW INDEX FROM northstar_beta_whitelist;
-- 删掉它，否则同一个 QQ 绑定第二个游戏ID 会被数据库拒绝
ALTER TABLE northstar_beta_whitelist DROP INDEX `qq`;
-- 已废弃的 UUID 列（保留也无害）
ALTER TABLE northstar_beta_whitelist DROP COLUMN player_uuid;
ALTER TABLE northstar_verify_log     DROP COLUMN player_uuid;
```

> **尚未上线过就最简单**：
> `DROP TABLE northstar_beta_whitelist; DROP TABLE northstar_verify_log;`
> 让服务重建即可（白名单本来也要重新导入）。

### 5.3 白名单条目从哪来：审批自动同步

服务端**不启用 MC 白名单，也不校验 UUID**，判定完全在后端完成。因此「内测审批通过」必须落到
白名单表，否则玩家会被判「未通过」而客户端崩溃——这正是 v3.1 之前的结构性问题：
白名单是运营手工维护的孤岛，与注册 / 审批数据零联动，玩家在平台注册、被批准、进游戏照样崩溃。

v3.1 起来源由 `source` 列区分：

| `source` | 来源 | 谁维护 |
| --- | --- | --- |
| `account` | 注册平台提交的 QQ + 离线服游戏 ID，审批通过后由 `BetaWhitelistService.syncApprovedPlayer` 写入 | 系统，重新审批会按最新值重建 |
| `manual` | 后台手工新增 / 批量导入 | 运营（历史数据该列为 NULL，按 `manual` 处理） |

同步的幂等规则：

1. 已存在完全相同的 `(qq, mcId)` 条目 → **不动**，连运营改过的启用状态与到期时间都保留
2. 否则删除该 QQ 下所有 `source=account` 的旧条目，按当前值重建一条「启用、永不过期」的条目
   ——这样玩家改了游戏ID 或 QQ 之后不会留下旧的通行证
3. `manual` 条目**永不**被系统删除

触发点共四处：

| 触发 | 位置 | 同步失败时的行为 |
| --- | --- | --- |
| 审核申请通过 | `AdminService.decideBetaApplication` | **抛错让审批回滚** |
| 后台直接发放 | `BetaService.grantBetaAccess` | **抛错** |
| 管理员改账号（QQ / 游戏ID / 内测状态） | `AdminService.updateUser` | **抛错** |
| 注册 / 改绑时认领已有资格 | `BetaService.claimApprovedEligibility` | 只记 WARN 日志，不打断玩家注册 |

反向操作（v3.3）：**账号从「已通过」变成别的状态时，系统同步的条目随之删除**（见 §5.5），
`manual` 条目永不触碰。

失败分两类：`MISSING_QQ`（账号没填 QQ）与 `INVALID_FORMAT`（QQ 或游戏ID 格式非法）。
**账号必须先有 QQ 才能获批**——QQ 缺失时审批会被拒绝并提示先去补填，宁可审批失败，
也不留下「后台显示已批准、玩家进游戏却被判未通过而崩溃」这种难查的状态。

QQ 的来源：注册平台在注册时要求填（`RegisterRequest.qq` → `users.qq`）；
**QQ 一个账号只允许绑定一次，绑定后不可更改**（见 §5.4）。
格式判定统一走 `support/QqFormat`（配置项 `northstar.verify.qq-pattern`），
避免出现「注册能过、白名单导入却报错」这类不一致。

### 5.4 QQ 与 Minecraft ID 都只允许绑定一次

规则：**一个账号的 QQ 与 Minecraft ID 各只允许绑定一次，绑定后玩家不可自行更改。**
v3.2 只覆盖了 QQ，v3.3 把 Minecraft ID 纳入同一份规则——理由完全一样：白名单以
`(qq, mcId)` 为键，两项都是内测资格凭据，允许改绑就等于允许把资格转手。

判定集中在 `support/OnceBinding`，用 `OnceBinding.Field`（`QQ` / `MC_ID`）区分字段，
注册、改资料、绑定游戏账号、后台管理四条路径共用同一份逻辑，避免某一处漏改就绕过去。
两个字段彼此独立：绑定 QQ 不会顺手把 ID 也算成已绑定，管理员的强制改写也只作用于指定字段。

| 入口 | 行为 |
| --- | --- |
| 注册（`AuthService.register`） | 提交即视为首次绑定，QQ 写 `qq_bound_at`、ID 写 `mc_id_bound_at`；ID 还会校验是否已被他人占用 |
| 改资料（`AuthService.updateProfile`） | 未绑定 → 写入；已绑定且值不同 → **抛错**；值相同 → 幂等返回；空值 → 不生效（不能借此解绑） |
| 绑定游戏账号（`AuthService.bindGameAccount`） | 与上一条同规则：换一条接口不能绕过限制 |
| 后台（`AdminService.updateUser` / `BetaService.grantBetaAccess`） | `OnceBinding.forceSet`：唯一的强制通道，玩家侧无此路径。每次真的改动都写 INFO 日志（谁、从什么改成什么）；传空串即解绑，玩家可重绑一次 |

为什么不让玩家改：白名单以「QQ + 游戏ID」为键，这两项就是内测资格的唯一凭据。允许改绑等于
允许把资格转给他人。代价是玩家自己填错就卡住了，所以留了管理员强制通道，并在前端把
「绑定后不可更改」写进二次确认与注册页提示里。

格式判定统一走 `support/McIdFormat`（`^[a-zA-Z0-9_]{3,16}$`）。在 v3.3 之前这条规则在注册、
绑定游戏账号、后台编辑玩家、后台发放内测、白名单录入里各写了一份，很容易出现
「注册能过、白名单导入却报错」这类不一致。

**错误消息必须原样回到前端**：`PUT /api/auth/profile` 原本没有 try/catch，抛出的
`RuntimeException` 会落进 Spring 默认错误响应（500），前端只能提示「更新失败」。
现在与登录 / 注册 / 绑定游戏ID 一致，返回 400 + 原文，玩家能直接看懂该怎么办。

### 5.5 内测资格与客户端白名单同进同退

两条不变式：

1. **账号「已通过」⇒ 白名单必须有对应条目**（缺 QQ 直接抛错让操作失败，
   不留下「后台显示已批准、玩家进游戏却被判未通过而崩溃」的状态）
2. **账号从「已通过」变成别的状态 ⇒ 系统同步的条目必须消失**（否则「取消」只是一句空话）

两条都收在 `AdminService.applyBetaWhitelistSideEffects` 这一个出口，避免「改状态 / 改 QQ /
改游戏 ID」三种操作各写一遍而漏掉某种组合。调用方传的是**改动前与改动后**两组身份值：
管理员可能在同一笔操作里既改了 QQ / 游戏ID 又取消了资格，只按当前值删会留下用旧值建的
孤儿条目，那条记录会一直在白名单里放行。

判定入口与边界：

| 方法 | 作用 | 边界 |
| --- | --- | --- |
| `BetaWhitelistService.syncApprovedPlayer` | 按当前身份写入 / 重建条目 | 只重建 `source=account`，人工条目不动 |
| `BetaWhitelistService.revokeAccountEntries` | 按给定身份删除系统条目 | 只删 `source=account`；返回删除条数，0 表示本来就没有（幂等） |
| `BetaWhitelistService.describeQualification` | 玩家自查：`active` / `disabled` / `expired` / `missing` | 不限流、不写日志；挑选口径与 `verify` 一致 |
| `AdminService.syncApprovedAccounts` | 全量对账：补缺失 + 清孤儿 | 人工条目完全不参与 |

对账是给历史数据用的：v3.1 之前「已批准但没白名单」和「已取消但白名单还在」两种漂移
都可能存在，靠 `POST /api/admin/beta/whitelist/sync-accounts` 一次修平，不必逐个人工核对。

### 5.6 申请内测必须登录，且身份只能是申请人自己

规则一句话：**有开放中的计划 → 登录平台账号 → 才能提交申请**。

这条规则要在服务端落地，而不是只把前端按钮藏起来。两道闸门：

| 闸门 | 位置 | 表现 |
| --- | --- | --- |
| 未登录不能申请 | `SecurityConfig`：`/api/beta/apply` 与 `/api/beta/my-application` **不在** `permitAll` 名单里，落到 `anyRequest().authenticated()` | 匿名请求 403，且**不会**在库里留下申请记录 |
| 身份不能代填 | `BetaService.applyForBeta` | 用户名 / QQ / 游戏 ID 全部读 `users` 表（`userId` 取自 JWT），请求体里的 `query` 被忽略 |

第二道闸门是关键：申请记录挂在 `users.id` 上，如果身份从请求体取，任何人都能拿别人的 QQ
和游戏 ID 去占名额。现在 `app.setQq(user.getQq())` / `app.setMcId(user.getMcId())`，
`BetaApplyRequest.query` 保留字段只是为了兼容仍在使用的旧前端包（已标 `@Deprecated`），
新调用方不必传。

**通知邮箱是唯一的例外**：`app.setEmail(req.getEmail())` 仍取请求体，允许玩家把审核结果
发到另一个地址；前端默认带出账号邮箱，玩家不改就直接用账号邮箱。

配套的 `GET /api/beta/my-application` 解决「已申请的人看不见自己申请过」：

| 返回字段 | 用途 |
| --- | --- |
| `hasApplication` | `false` ⇒ 前端显示申请表单（全新账号就是这一态） |
| `status` | `pending` ⇒ 显示「审核中」状态卡；`denied` ⇒ 允许换计划重新申请 |
| `planName` / `planPhase` / `createdAt` / `email` | 「审核中」卡片上的回执信息 |
| `betaStatus` | 账号当下的资格，与 `status` 分开——管理员可以不给申请记录就直接发资格 |

`planName` 用 `BetaPlanService.findPlan`（查不到返回 `null`）而不是 `requirePlan`：
计划的 id 是申请时的历史快照，运营把计划删掉之后玩家的申请还在，这时不能因为计划找不到
就把整个查询接口炸成 500。

## 8. 已知取舍

- **「游戏ID」比 UUID 更弱**：离线模式下玩家名是玩家自己可改的，因此「QQ + 游戏ID」只能证明
  "知道这个 QQ 且用了这个名字"，不等于强身份。要绑定真正的人，建议在发号环节人工核对游戏ID。
  v3.1 起游戏ID 取自注册平台提交值（`users.mc_id`），比运营手填更可追溯，但**仍是玩家自报**，
  性质没有变化。
- **限流是单机内存滑动窗口**：重启清零、多实例不共享。当前规模够用；
  若横向扩容，建议换成 Redis 计数（项目已引入 `spring-boot-starter-data-redis`）。
- **接口无鉴权令牌**：知道地址即可查询「某 QQ+游戏ID 是否有资格」。若需更强防护，
  下一版可加 HMAC-SHA256 签名（对 `qq|name|timestamp` 用共享密钥签名，**签名里不含 UUID**），
  需 Mod 侧同步改动。
- **本验证是客户端行为，可被绕过**（改配置 / 抓包 / 删 `verification.json` / 反编译 Mod）。
  它适合做**内测资格分发与统计**，**不能当作多人服务器的安全边界**。
  真要防未授权进入，必须在服务端做校验。
